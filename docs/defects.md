# Разбор пяти намеренных дефектов

Исходное состояние — коммит шаблона `hw3-broken` (до правок ДЗ). Симптомы из `README.md`; строки в задании не указаны. Ниже: где был дефект, как проявлялся, чем исправлен, каким числом это видно.

## 1. Данные попадали в git

**В чём был.** В `.gitignore` не было каталогов `data/` и `dataset/`. Стадия `collect` пишет `data/raw.jsonl`, `clean` и `split` — остальные JSONL. При `git add . && git commit` эти файлы оказывались в истории.

**Как проявлялся.** `git log --stat` показывал крупные JSONL. Проверка 1 в `make check` считала `git ls-files data/` и требовала строку `data/` в `.gitignore`. Remote DVC тоже не был задан: в `.dvc/config` не было `remote`, выгружать данные было некуда.

**Как исправлен.**

- В `.gitignore`: `data/`, `dataset/`, плюс мусор `*.bak`, `*.orig`.
- В `.dvc/config`: local remote `storage` → `../dvc_remote`.
- В `dvc.yaml` у стадии `split` в `outs` добавлены `data/val.jsonl` и `data/test.jsonl` (раньше был только train — val/test не версионировались).

**Чем подтверждается.** `git ls-files data/` пуст; проверка 1 зелёная. В истории нет коммитов с JSONL из `data/`. Размеры артефактов v2: `raw.jsonl` ≈ 15.9 МБ, `clean.jsonl` ≈ 15.4 МБ — такие файлы в git быть не должны.

## 2. Смена версии данных не пересчитывала пайплайн

**В чём был.** У стадии `collect` в `dvc.yaml` не было `params`, в `deps` не было файлов источника, не было `metrics`. У стадии `clean` в `deps` не было `data/raw.jsonl`. Версия живёт в `params.yaml` → `collect.version`. DVC смотрит только на объявленные deps/params: смена `v1` → `v2` не инвалидировала стадии.

**Как проявлялся.** `dvc repro` после правки версии писал, что пересчитывать нечего. `data/clean.jsonl` оставался от прошлой версии. Проверка 4 сравнивает MD5 `clean.jsonl` после `set_version.py v1` и `v2`.

**Как исправлен.**

- `collect.deps`: `dataset/Questions.csv`, `Answers.csv`, `Tags.csv`, плюс код.
- `collect.params`: секция `collect` целиком (там `version`, `n_rows`, `max_per_topic`).
- `collect.metrics`: `metrics/collect.json`.
- `clean.deps`: добавлен `data/raw.jsonl` (без этого смена raw не гоняла бы чистку).

**Чем подтверждается.** v1: `rows_in = 2200`, hash `clean.jsonl` один; v2: `rows_in = 6000`, hash другой. Проверка 4 зелёная, если MD5 не совпадают. `make diff` показывает рост `collect.rows_written` 2200 → 6000 и `clean.rows_out` 2179 → 5934.

## 3. Контаминация train/test

**В чём был.** `src/split.py` резал **по строкам** (`row_split`: shuffle индексов, нарезка по долям). `split.group_key: topic` читался и клался в метрики, но на раскладку не влиял. Вопросы одной темы — парафразы; тема ещё и входит в смысл вопроса.

**Как проявлялся.** `scripts/check_contamination.py` находил пересечение по группам и/или near-dup пар. На лекции случайный сплит дал 19.5% утечки в test, сплит «как будто по темам» без дедупликации — 12.3%. Единственный симптом на обучении — завышенная метрика на test. Проверка 5 валится, если гейт возвращает ненулевой код.

**Как исправлен.** Сплит целыми группами: `normalize_group(topic)`, жадная раскладка крупных групп в сплит с наибольшим остатком ёмкости (`group_split`). Порог near-dup в `contamination.threshold` совпадает с `clean.near_dup.threshold` (0.85). Скрипт проверки — отдельный гейт (`make contamination`), не строка в логе.

**Чем подтверждается.** `metrics/split.json` (v2): `id_overlap = 0`, `text_overlap = 0`, `group_overlap = 0`, `near_dup_pairs = 0`; размеры 4748 / 593 / 593, групп 85 / 20 / 20 (темы не пересекают границу сплитов). Проверка 5 зелёная.

## 4. Почти-дубли переживали очистку

**В чём был.** В `src/clean.py` шаг 5 был TODO: `near: set[int] = set()`, `near_duplicates` из `src/dedup.py` не вызывался. Работала только точная дедупликация по `normalize_text(user)`. Пара «тот же вопрос, другие пробелы/нумерация вариантов» имеет разный точный ключ и оставалась дважды.

**Как проявлялся.** На курсовом НМО-наборе точный хэш находил 0 дублей, сравнение нормализованных вопросов — 11 626 повторов. Проверка 2 подкладывает точный дубль, near-dup и три ПДн; требует `dropped_exact_dup ≥ 1`, `dropped_near_dup ≥ 1`, сумма `pii_hits ≥ 3`.

**Как исправлен.** После точного шага: MinHash + LSH по тем же нормализованным текстам, параметры из `clean.near_dup` (`shingle_words=4`, `num_perm=64`, `threshold=0.85`). ПДн маскируются **до** дедупликации: строки, отличавшиеся только телефоном, схлопываются.

**Чем подтверждается.** Проверка 2 на синтетическом входе. На собственном Cross Validated после сужения `dropped_exact_dup = 0`, `dropped_near_dup = 0` — в этом срезе почти-дублей нет, но стадия обязана существовать: иначе проверка 2 красная.

## 5. Гейт разнообразия не был гейтом

**В чём был.** `src/diversity.py` уже считал пороги и собирал `violations`, но в `main` при нарушениях стоял TODO: печаталось предупреждение, процесс завершался с кодом 0. Вырожденный набор (один system prompt, одна тема, ответы одной длины) доезжал до split и обучения.

**Как проявлялся.** Проверка 6 подкладывает 1200 валидных разных строк с одной темой и одним промптом. Если стадия проходит — гейт не работает. Если падает, в stderr должны быть формулировки вроде «системных промптов», «групп», «длин ответа», «одну и ту же длину» (не меньше двух совпадений).

**Как исправлен.** При непустом `failed` стадия бросает `DiversityError` со списком порогов и фактов. Метрики пишутся до исключения, чтобы было что читать. Пороги в `params.yaml` не занижались «чтобы позеленело».

**Чем подтверждается.** Проверка 6 падает на вырожденном наборе и называет несколько порогов. Проверка 7 на нашем clean (v2: 5934 строки, 5 промптов, 125 групп, largest share 1.58%, p90/p10 = 8.38) проходит.
